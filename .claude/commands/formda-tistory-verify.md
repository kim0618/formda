# /formda-tistory-verify [번호들]

예: `/formda-tistory-verify t1-t5`

순서: `/formda-tistory`(작성) → **`/formda-tistory-verify`(재검증)** → `/formda-tistory-publish`(예약). 제이퍼 `/tistory-verify`를 옮긴 것이고, 숫자 검증 대신 법 조항·서식·도구 동작 검증이 중심이다. 모든 단계는 Opus로 한다(11/20 사용자). 그래서 독립성은 모델을 바꾸는 대신 **작성 맥락이 없는 새 에이전트**로 만든다.

## 왜 따로 하나
작성한 세션이 같은 방법으로 다시 보면 같은 걸 놓친다. 제이퍼는 11/20 재검증에서 5편 중 4편의 틀린 내용을 잡았다. 검증자는 원고와 도구 페이지·법령만 보고, 작성자의 계산이나 결론을 받지 않는다.

## 절차

### 1. 대상 확인
`~/formda/tistory/queue.md`에서 대상이 "작성 완료(발행 대기)"인지 본다. `posts/tNNN-*.html`, `meta/tNNN.txt`가 있어야 한다.

### 2. 독립 검증 에이전트 (편마다 1개, 병렬)
Agent 도구(subagent_type: general-purpose)로 편마다 하나씩 띄운다. 프롬프트에는 **아래 템플릿만** 넣는다. 작성 때 뽑은 숫자, 큐의 축 설명, 내 판단은 넣지 않는다.

```
너는 블로그 원고 검증자다. 원고를 쓴 사람의 설명은 받지 않는다. 파일만 보고 독립적으로 확인한다. 원고 파일은 고치지 말고 결과만 보고한다.

원고: /home/tjd618/formda/tistory/posts/<파일>
메타: /home/tjd618/formda/tistory/meta/<tNNN>.txt (제목 포함)
도구: 원고 링크의 https://formda.kr/tools/<slug> (문서 작성 도구. 구현은 /home/tjd618/formda/engine/, 설명은 /home/tjd618/formda/data/registry.js(2차 출처라 틀릴 수 있음))
쓸 수 있는 것:
- 도구 페이지 실행: cd /home/tjd618/formda/tistory && LD_LIBRARY_PATH=$HOME/.local/emulib node run.mjs <slug> <expr.js>  (입력칸 id는 f-<키>, set(id, 값)·sleep(ms) 제공, 마지막 식이 JSON 출력. 미리보기 문서는 #doc)
- 법령 원문: LD_LIBRARY_PATH=$HOME/.local/emulib node /home/tjd618/jptcalc/scripts/law-render.mjs <법령명> <출력경로>  → <출력경로>.txt 에서 조문 검색
- 그 밖에 python3로 직접 계산

할 일:
1. 법·제도 주장(조문 번호, 기간, 비율·한도, 시행일, 서식 필수 항목, 효력·무효·처벌 관련 문장)을 원문으로 대조한다. 원문을 못 찾으면 "미확인". 추측으로 맞다고 하지 않는다.
2. 숫자(금액·부가세·이자·지연손해금·날짜·요일·기한·합계)를 전부 뽑아 직접 다시 계산한다.
3. 도구에 관한 서술(칸 이름, 자동으로 해 주는 것, 저장 형식, 파일명)을 실제 페이지(run.mjs)나 engine 구현과 대조한다.
4. 일반화·단정("대부분", "보통", "항상", "법적 효력이 있다", "무효")에 근거가 있는지 본다.
5. 캡처 설명(회색 줄)과 meta ALT가 본문 예시와 맞는지 본다.

보고 형식(이것만):
- 틀림: 원문 문장 / 올바른 내용 / 근거(조문 또는 계산식 또는 구현 위치)
- 미확인: 원문 문장 / 왜 확인 못 했는지
- 과한 단정: 원문 문장 / 제안
- 확인 완료: 확인한 주장·숫자 개수
```

### 2-2. 문체·반복 패턴 검증 에이전트 (묶음당 1개, 2와 동시에)
숫자 검증과 별도로 하나 더 띄운다. 한 편씩 보면 반복이 안 보이므로 **이번 묶음 + 직전에 쓴 글 전부**를 나란히 읽게 한다. 역시 작성 의도·내 판단은 주지 않는다.

```
너는 블로그 원고의 문체 검증자다. 쓴 사람의 설명은 받지 않는다. 원고 파일은 고치지 말고 결과만 보고한다.

규칙: /home/tjd618/formda/tistory/rules.md 의 §11(품질·AI 티·틀 반복) 을 먼저 읽는다.
이번 검증 대상: <대상 파일 목록>
비교 대상(이미 쓴 글): /home/tjd618/formda/tistory/posts/ 안의 나머지 t*.html 전부
(본문 HTML에서 [[TOPIMG]]·[[CAPTURE1]]·스페이서 문단은 무시)

할 일:
1. AI가 쓴 티: 사람이 잘 안 쓰는 상투어·번역투·빈 강조·기계적 대칭(같은 길이 문단, 3개짜리 목록 반복, 모든 소제목 아래 같은 구조), 지나치게 매끈한 연결어, 근거 없는 공감 멘트를 문장 단위로 찾는다. 규칙의 금지어 목록에 없어도 어색하면 적는다.
2. 글끼리 반복: 대상 글과 비교 대상 글 사이에서 겹치는 것을 찾는다.
   - 도입 첫 2~3문장의 구조(예: "X면 Y예요. 그런데 Z" 꼴이 여러 편)
   - 소제목 패턴, 끝맺음 방식, 글쓴이 단락·기준 줄·CTA 문장의 틀
   - 자주 반복되는 문장 골격·어휘(예: "~이유입니다", "~셈이에요", "숫자로는 이 정도", "~라는 뜻이에요")를 편별 횟수와 함께
   - 문장 길이·리듬이 편마다 똑같은지
3. 독자가 "다른 블로그와 똑같다"고 느낄 지점(정보 나열만 있고 판단이 없는 구간 등).

보고 형식(이것만):
- AI 티: 파일 / 원문 문장 / 왜 / 고친 예
- 반복 패턴: 무엇이 / 어느 파일들에서(횟수) / 바꿀 방향
- 그대로 둬도 되는 것: 한 줄
- 전체 평가: 대상 글 각각 상·중·하와 이유 한 줄
```

### 3. 결과 처리 (메인 세션)
- **틀림**: 검증자의 근거를 내가 한 번 더 확인한 뒤(검증자도 틀릴 수 있다) 원고를 고친다. 내용을 고치면 연결된 제목·meta TITLE/ALT·대표이미지(make_thumb)·캡처 설명·캡처 setup도 같이 고친다.
- **미확인**: 내가 원문을 찾아 확인한다. 못 찾으면 그 문장을 빼거나 "~로 안내돼 있어요"처럼 출처를 밝힌 표현으로 낮춘다.
- **과한 단정**: 근거가 없으면 고친다.
- **AI 티·반복 패턴**: 지적 문장을 다시 쓴다. 같은 틀이 여러 편이면 이번 묶음 쪽을 바꾼다(이미 발행된 글은 그대로). 글쓴이 단락·기준 줄·CTA처럼 매 편 들어가는 부분도 문장 틀을 돌려 쓴다. 고친 뒤 숫자가 바뀌지 않았는지 확인한다.
- 문체를 크게 고친 편이 있으면 문체 검증만 한 번 더 돌린다(최대 2회).
- 고친 뒤 `python3 check_post.py posts/tNNN-*.html` + `node mobile_check.mjs posts/tNNN-*.html` 다시 PASS.
- 고친 게 숫자라면 그 편만 검증 에이전트를 한 번 더 돌린다(최대 2회).

### 4. 기록·보고
- `queue.md` 상태 "검증 완료(발행 대기)".
- `ledger.tsv`는 건드리지 않는다(발행 때 기록).
- 사용자에게: 편별로 확인한 개수, 고친 것(전→후, 근거), 뺀 것, 미확인으로 남긴 것, 문체 평가(상·중·하)와 고친 반복 패턴. 이어서 `/formda-tistory-publish`로 예약하면 된다고 안내.

## 하지 말 것
- 검증 에이전트에게 작성 때 숫자·결론을 주기(독립성 깨짐).
- 검증자의 지적을 확인 없이 그대로 반영하기.
- 크롬 열기(발행은 /formda-tistory-publish).
- 이미 예약된 글이면 고친 뒤 `/formda-tistory-publish --update`가 필요하다고 반드시 말하기.
